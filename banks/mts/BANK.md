## 1. Производитель и метаданные

Каждый чек — выхлоп одного и того же серверного пайплайна:

```
PDF 1.5, producer: OpenPDF 1.3.30.jaspersoft.2, creator: dbo-print-forms
author: MTS Bank, title: "Printable document"
subject: "CorrelationId:<16 hex lowercase>"   (случайный per-документный id)
CreationDate == ModDate == "D:YYYYMMDDHHmmSSZ" (UTC, суффикс Z)
```

- `CreationDate` — **момент выгрузки** (скачивания), не момент операции:
  у всех трёх доноров 07.11 ~06:38–06:39 МСК при операциях ночью/вечером.
  Движок ставит момент генерации (как у Яндекса/Рокета).
- CorrelationId — 16 hex; свежий на каждую генерацию.
- Трейлерный `/ID` — два 32-hex случайных значения; свежие.
- Страница одна, 375×720 pt; фон — белый с красной полосой, логотип
  (форма `Xf1` + картинки) и QR-код СБП — статичные объекты.

## 2. Физическая структура (детерминирована между донорами)

Номера и порядок объектов совпадают у всех доноров; меняются только
длины переменных потоков и байты координат/строк:

```
%PDF-1.5\n%\xe2\xe3\xcf\xd3\n
4..23  — картинки логотипа (байт-статичны)
3      — форма логотипа Xf1
24     — пиксель-маска (img20)
27/28  — QR (img21/img22, 563×246 + SMask)
29     — контент-стрим страницы        (переменная длина)
53/56  — FontFile2 + ToUnicode MTSSans-Regular   (переменные)
57/60  — FontFile2 + ToUnicode MTSSans-Medium    (переменные)
63     — каталог  <</Names 62 0 R/Type/Catalog/Pages 30 0 R/ViewerPreferences<</PrintScaling/AppDefault>>>>
64     — Info (см. выше)
31     — ObjStm со всеми «мелкими» объектами (32 штуки, порядок фикс.)
65     — xref-ПОТОК <</Info 64 0 R/Type/XRef/W[1 2 2]/Index[0 66]/ID[..]/Root 63 0 R/Size 66>>
startxref … %%EOF\n
```

Особенности xref-потока: `/Index[0 66]`; записи типа 2 (в ObjStm 31) для
объектов 1,2,25,26,30,32–52,54,55,58,59,61,62; **свободные записи
(тип 0, gen 65535) у объектов 0 и 65** — xref-стрим помечает сам себя
свободным, это штатная особенность OpenPDF.

ObjStm (объект 31), порядок членов фиксирован:
`1 (Page) → 32..52 (21 named dest) → 2 (Helvetica) → 54,55,25
(дескриптор, CIDFont, Type0 Regular) → 58,59,26 (то же Medium) →
30 (Pages) → 61 (/Names) → 62 (<</Dests 61 0 R>>)`.
Индекс — пары `num off ` с пробелом после каждой; тела разделены
одиночным пробелом (включая хвостовой).

Сжатие: **все потоки — zlib level 6** (Java Deflater default):
`zlib.compress(data, 6)` воспроизводит все 32 потока донора байт-в-байт.

## 3. Поля чека

Блока отправителя нет (только «Счет списания»). Все значения —
**MTSSans-Regular 12 pt**, правый край x=355; подписи слева x=20;
«Итого» — MTSSans-Medium 20 pt; шапка-дата серая (0.50196).

| Поле | y (baseline) | Пример | Примечания |
|---|---|---|---|
| шапка-дата | 643.35 | `07.11.2026 01:16:03 (UTC+3)` | МСК, секунды; серый |
| Получатель | 597.35 | `Никита Валерьевич У` | форма «Имя Отчество Ф» **без точки** |
| Телефон получателя | 565.35 | `+7 (993) 134-95-57` | скобки, в отличие от Рокета |
| Банк получателя | 533.35 | `Т-Банк` / `Озон Банк (Ozon)` | короткие имена СБП-справочника |
| Сообщение | 501.35 | `Перевод СБП` | дефолт при пустом комментарии |
| Счет списания | 469.35 | `40817 81020 00025 66548` | 20 цифр группами 5-5-5-5 |
| Сумма | 437.35 | `15,00 ₽` | копейки всегда, запятая |
| Комиссия | 405.35 | `0,00 ₽` | у всех доноров 0 |
| Код транзакции | 373.35 | `019544730490` | 12 цифр, счётчик банка |
| Код операции СБП | 341.35 (+325.77) | 32 символа, **перенос на 2 строки** | бокс 167 pt (188..355) |
| Итого | 260.58 | `15,00 ₽` | Medium 20; = Сумма при fee 0 |

Геометрия подтверждена вычислением по метрикам шрифта на всех полях
всех доноров: `x = 355 − width(text)×size/1000`, печать координат —
`ByteBuffer.formatDouble` OpenPDF (округление half-up до 2 знаков,
хвостовые нули срезаны). Перенос СБП-ID: первая строка — самый длинный
префикс ≤ 167 pt (по донорам 22–26 символов), остаток — второй строкой;
бокс 188..355 (167 px при 72 dpi у JasperReports).

**Отклонение первой строки СБП (±0.006 pt).** Координата x первой
строки СБП-ID у настоящих чеков несёт шум ±0.006 pt от
AWT/JasperReports-пайплайна (правый край этой строки по 12 донорам
гуляет 354.996–355.006 вместо ровно 355.000, шаг 0.002 pt; механика —
`TextLayout.getVisibleAdvance()` + `PdfPhrase.go` с
`leftOffsetFactor=-0.2f` в JRPdfExporter). Из-за этого в ~25% случаев
округление до 2 знаков флипает на 0.01. Это единственный байт, который
не воспроизводится из первых принципов; в identity-режиме round-trip
наследует донорское значение (`save(sbp_line1_x=...)`), в генерации
модельное значение всегда внутри настоящего разброса. Все остальные
координаты (включая вторую строку СБП) — точные.

## 4. /Names: именованные якори JasperReports

Каждый текстовый элемент несёт named destination: ключи — **тексты
полей и подписей**, значения — `[1 0 R/XYZ x y 0]` (x=старт текста,
y=baseline+size; у подписей x=20). Плюс фиксированный
`JR_PAGE_ANCHOR_0_1 → [1 0 R/XYZ 0 730 0]`. У второй строки СБП и у
значения «Итого» якорей нет.

Два OpenPDF-артефакта, воспроизводимых движком:

- ключи сериализуются **младшими байтами UTF-16** (`char & 0xFF`):
  `₽` U+20BD → байт 0xBD, `Б` U+0411 → 0x11 (сырой control-byte в
  файле!), экранируются только `( ) \` и \r \n \t \b \f;
- **сортировка по исходной строке** (Java String.compareTo), и
  **номера dest-объектов 32..52 присваиваются в этом порядке** —
  поэтому у донора 2 «Ильяс…» (U+0418) стал объектом 41, а «Итого»
  сдвинулось на 42. Движок пересчитывает сортировку и нумерацию на
  каждой генерации.

## 5. Шрифты

В чек встроены сабсеты `XXXXXX+MTSSans-Regular` и `XXXXXX+MTSSans-Medium`
(Type0/Identity-H, CID==GID, FontFile2). Сабсет-тег — **6 случайных
букв A–Z** (OpenPDF `createSubsetPrefix` = SecureRandom, доказано
исходником 1.3.30 и различием тегов между донорами), свой на каждый
шрифт и каждую генерацию.

Оригинал у банка — **MTSSans v1.0** (created 24.05.2019, 1000 upm,
351 глиф, rev 1.0): таблицы `head/hhea/maxp` и полная 351-записная
`hmtx` копируются OpenPDF в сабсет без изменений, поэтому они
восстановлены из доноров побайтно. Публично раздаётся только
**v1.003** (2048 upm, другие очертания — скачан, проверен, **не
подходит и удалён**; восстановить v1.0 из него нельзя: 33/55 глифов
имеют другую топологию точек).

Алгоритм сабсета (порт OpenPDF `TrueTypeFontSubSet`, проверен
байт-в-байт round-trip): CID = исходный GID; таблицы в порядке
`glyf head hhea hmtx loca maxp`; `glyf/loca` пересобираются под текст,
остальные — verbatim из v1.0; `/W` и ToUnicode — ровно под текст
строки (глифов отсутствующих в тексте нет), форматы — из
`TrueTypeFontUnicode`.

**Пул глифов — два источника:**

1. **Донорские сабсеты** (`donors/`) — побайтно точные контуры v1.0
   TTF-флейвора; всегда выигрывают. Покрытие 14 доноров: кириллица
   заглавные `А Б В Г Д Е Ж И К Л М Н О П Р С Т У Х Ю Я`, строчные
   `а б в г д е з и й к л м н о п р с т у ф х ц ч щ ь ю я`, латиница
   `A B C D E G O T U n o z`, цифры/пунктуация/₽; Medium — все цифры.
2. **Синтезированные контуры** (`fonts/MTSSans-*.otf`) — для символов
   вне донорского покрытия. Источник: **оригинальный бренд-пакет МТС
   `MTSSans_05otf_07_06_2019.zip` из Wayback Machine** (медиабанк
   moskva.mts.ru, снапшот 18.07.2019) — CFF/OTF-флейвор того же v1.0:
   `head.created=3641556680` совпадает с банковским TTF точно, rev 1.0,
   1000 upm; GID-раскладка `ttf_gid = otf_gid + 2` (проверена на всех
   донорских символах обоих начертаний). Конверсия CFF→quadratic:
   cu2qu, `max_err=1.0`, `reverse_direction=True` (TT-соглашение о
   направлении контуров). Очертания визуально идентичны банковским,
   но **не побайтовы** (у TTF-флейвора собственная точечная топология;
   cu2qu даёт больше точек). Синтезированные GID помечены в
   `FontPool.synthetic_gids`; ширины берутся из донорской 351-записной
   `hmtx` (точные). Если проверяющий когда-либо пометит глифы —
   отключается `build_pool(synthetic=False)` и возврат к модели
   «только доноры».

Покрытие с обоими источниками: **вся кириллица и латиница OTF-флейвора
(349 глифов)**. Символ вне обоих — честный отказ
(`GlyphCoverageError`).

## 6. Детерминированные идентификаторы

- **Шапка-дата vs СБП-ID**: печатное время опережает закодированный в
  СБП-ID UTC-момент на несколько секунд; по 12 донорам дельта
  **+3..+29 с** (3,6,6,6,8,9,12,13,15,15,15,29). Движок: SBP-момент =
  header − U[3..29] с; при нулевых секундах у пользователя секунды
  наследуются от свежего донора (как у Рокета), потом прибавляется
  дельта.
- **СБП-ID** (32 символа): `[A/B][год][день года][ЧЧММСС UTC]`
  + серийная часть: 3 цифры (12–14), цифра (15),
  `{C,E,2,O,D,T,0,4,9}` (16), маркер эпохи (17–18), сегмент (19–22)
  из `{1001,1002,1003,1004,1012}`, хвост эпохи (23–32). Серийная часть
  перемешивается **в алфавите донора** (символы покрываются глифами
  операционного шрифта, новых букв не появляется). Эпоха — системная,
  совпадает с Рокетом/Яндексом: `0B/…/0011881102` до 05.11
  включительно (доноры 3–12), `0G/…/0011890101` с 06.11
  (доноры 1–2) — по UTC-дате операции.
- **Код транзакции** (12 цифр): счётчик банка, но **не строго
  монотонный во времени**: внутри одного утра префиксы 019461–019466
  перемешаны (09:55 → 019461913020, а 09:06 → 019466832560). Модель:
  якорь на самой свежей точке (07.11) + локальный наклон по двум
  последним точкам (~149/с) + джиттер; точное распределение требует
  ещё доноров.
- **CorrelationId** (Info Subject): свежие 16 hex на документ.
- **/ID**: два свежих 16-байтовых hex.
- **Имя файла**: у настоящей выгрузки — `Unknown.pdf` (сервер не
  отдаёт имя); движок по умолчанию пишет `out/Unknown.pdf` с
  дедупликацией `Unknown N.pdf`, как Safari.

## 7. Сохранение

Один проход, «natural save»: единственный xref-поток, один `%%EOF`,
никаких `/Prev`, инкрементальных хвостов и паддингов; сжатие потоков —
zlib level 6, как у оригинала. Размер выхода остаётся в коридоре
настоящих чеков (49.4–49.8 KB у доноров; у генераций — тот же коридор).

Доказательство этапов 2–3 (`test_mts.py`): каждый донор,
переизлитый с собственными значениями и метаданными, воспроизводится
**байт-в-байт** (3/3); смена суммы/всех полей даёт валидный
однопроходный файл с пересчитанными сабсетами, /Names и xref.

## 8. Движок `engine.py`

```python
generate_mts(
    amount,                    # 100 | "17,00 ₽" | Decimal -> "1 500,00 ₽"
    operation_dt,              # datetime МСК (naive = МСК); секунды опц.
    recipient_name,            # "Фамилия Имя Отчество" -> "Имя Отчество Ф"
    recipient_phone,           # любой RU формат -> "+7 (993) 134-95-57"
    recipient_bank,            # "Т-Банк" | "Сбербанк" | "Озон Банк (Ozon)" | …
    output_path=None,          # default out/Unknown.pdf (+ дедупликация)
    sender_account=None,       # 20 цифр; default — счёт донора
    message=None,              # default "Перевод СБП"
    donor_path=None, pool=None, generated_at=None,
    sbp_id=None, txcode=None,  # ручные переопределения (тесты)
) -> pathlib.Path
```

Выбор шаблона: самый свежий донор (по моменту в СБП-ID), который
набирает все строки своими глифами. Отказы: символ вне пула глифов
(какие буквы — в сообщении), невалидные сумма/телефон/счёт, дубликаты
текстов полей (невалидное дерево /Names), сумма > 999 999,99.

Ограничения, которые знаем и принимаем (снимаются новыми донорами):

- группировка тысяч в сумме — пробел (`1 500,00 ₽`, `50 000,00 ₽`):
  подтверждена пятизначными донорами 4–12;
- донорское покрытие глифов (§5) — полное для кириллицы/латиницы
  (доноры + синтез из CFF-мастера); символы вне OTF-флейвора —
  честный отказ;
- значения шире ~165 pt (очень длинные ФИО/сообщения) не проверены
  настоящими донорами — перенос таких полей не моделируем;
- комиссия всегда `0,00 ₽` и сообщение `Перевод СБП` по всем 14
  донорам — поведение полей при других значениях не проверено
  (нестандартное сообщение поле принимает, но покрытие/перенос —
  по тем же правилам).

## 9. Чего ждём от проверяющего

Сгенерированные чеки (`out/`) загружаются в @podlinno_bot (категория
МТС). При не-зелёном — меняем по одному фактору за раз: (1) эпоха/
хвост СБП-ID, (2) скорость счётчика транзакций, (3) дельта шапка↔СБП,
(4) CorrelationId/ID, (5) сабсет-теги, (6) группировка суммы,
(7) синтезированные глифы (`build_pool(synthetic=False)` = откат к
донорской модели), (8) покрытие глифов (новые доноры).
