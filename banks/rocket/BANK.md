# Рокетбанк — чек перевода через СБП

## Донор

- Настоящие доноры этого чата: `receipt_rocket 18.pdf` …
  `receipt_rocket 37.pdf` из `~/Downloads` (20 файлов, операции
  05.10–29.10.2026), а также свежие `receipt_rocket 41.pdf` и
  `receipt_rocket 42.pdf` (настоящие операции 03.11.2026 06:41/06:42
  МСК, владельцем проверяющему не показывались). Копии лежат в
  `donors/receipt_rocket_*.pdf`.
  Все — один тип чека: перевод через СБП, исходящий, без комиссии.
- Шаблон по умолчанию для `engine.py`: `donors/receipt_rocket_42.pdf`
  (свежий ноябрьский донор; маркер эпохи `0B` у него родной).
- Пул глифов собирается на лету из всех 20 настоящих доноров в `donors/`
  (плюс, как запасной источник тех же ракетовских шрифтов, старые
  `rocket_sbp_check.pdf` / `rocket_card_check.pdf` из этой папки).
  Готовый `rocket_glyphs.pkl` движку не нужен и может быть устаревшим.
- ⚠️ `rocket_sbp_check.pdf` и `rocket_card_check.pdf` в этой папке —
  **не настоящие доноры**, а результаты прежних генераций: у СБП-файла
  дата `06.10.2026 21:05`, сумма `1 500 ₽` и получатель
  «ИВАН ПЕТРОВИЧ К», но `sbp_id` байт-в-байт совпадает с настоящим
  донором № 29 (операция 05.10.2026 03:42 МСК), номер документа —
  круглая заглушка `M70123456789` из старых тестов, а CreationDate
  раньше самой операции. Как эталон полей их использовать нельзя.

## Чем сделан оригинал

- Producer: iText® Core 9.1.0, PDF 1.7, одна страница, классический xref:
  у всех 20 доноров ровно 1 `startxref` и 1 `%%EOF`, 181 объект,
  размер 88 779–89 421 байт.
- Info: только `CreationDate`, `ModDate` (всегда равны между собой,
  формат `D:YYYYMMDDHHmmssZ`) и `Producer`. Trailer `/ID` — два
  одинаковых 128-hex значения, у каждого файла своё.
- У корпуса 18–37 CreationDate — момент выгрузки/скачивания
  (03.11.2026 01:19–01:25Z при операциях 05–29.10), а не момент
  операции: PDF пересоздаётся при выгрузке чека. Связи «CreationDate =
  операция + N» в этом корпусе нет; проектная конвенция «операция +
  5 минут» (как у Яндекса и старого корпуса Рокета) сохранена в движке
  как допустимая, см. «Гипотезы».
- Каждая строка — свой шрифтовой сабсет: дата и все подписи/значения —
  `RocketMono-Regular` 14 pt, сумма — `RocketSans-Wide` 19 pt.
  Поля адресуются по серой подписи над значением
  (`rocket_receipt.LABEL_FIELDS`), шрифты — CID-сабсеты CFF, обычный
  поиск по байтам значения не находит.

## Правила связности (по 20 донорам)

### Идентификатор операции СБП (32 символа)

Декодирование по позициям (1-based), подтверждено на всех 20
(пример: `A63021527453300N0G10030011880703` = операция
29.10.2026 18:27:45 МСК):

| Позиции | Значение | Связь |
|---|---|---|
| 1 | `A` или `B` | буква заголовка; наследуется от донора вместе с серийной частью |
| 2 | последняя цифра года | **UTC**-год операции |
| 3–5 | день года, 3 цифры | **UTC**-дата (13.10 01:32 МСК → день 285, ещё 12.10 UTC) |
| 6–11 | `ЧЧММСС` | **UTC**-время (МСК−3); секунды в чеке не печатаются — если момент задан без секунд, движок наследует секунды донорского ID, как патчер Яндекса |
| 12–14 | 3 цифры | серийная часть ОПКЦ, наследуется от донора |
| 15 | `0` | константа у всех 20 (первая версия движка ошибочно ставила сюда 4-ю случайную цифру — это и ломало «номер операции») |
| 16 | символ из набора `134679BCKN` | серийная часть; распределение скошено (`7` — 5 из 20), но отдельно не перебрасывается |
| 17 | `0` | константа у всех 20 |
| 18 | `B` или `G` | серийная часть (маркер маршрута/поколения), наследуется |
| 19–22 | только `1001,1002,1003,1004,1006,1007,1012,1014,1017,1018,1020` | серийная часть; значения вроде `1019` в корпусе Рокета не встречаются |
| 23–32 | `0011860303`, `0011870501` или `0011880703` | серийная часть; хвосты растут «поколениями» со временем |

Формула генерации: временной заголовок перестраивается всегда;
серийная часть — по эпохе операции: для дат до 03.11.2026 наследуется
от донора, с 03.11.2026 ставится актуальный профиль ОПКЦ
`…0B + 1004 + 0011881102` (свежие чеки МТС владельца, см. полный
анализ в «Что не проходит проверку»). Случайная сборка серийной
части из наблюдённых алфавитов/частот (версии 4–5) создавала
комбинации сегментов, которых ОПКЦ никогда не выдавал, и стабильно
держала пункт «номер операции» оранжевым.

#### Логика СБП-ID — что установлено точно

- Из открытых норм: идентификатор перевода присваивает **ОПКЦ**
  (АО «НСПК»), он обязан однозначно идентифицировать распоряжение
  в течение дня (Альбом распоряжений ЦБ, реквизит 3 поручения для
  СБП); публичного алгоритма серийной части нет — это закрытая
  техническая спецификация НСПК для участников.
- Детерминированная часть — только заголовок выше (UTC дата/время
  до секунд; проверено декодированием всех 23 уникальных ID
  Downloads и 40 ID чеков Яндекса из корня проекта: устройство
  заголовка у системы одно).
- Серийная часть (поз. 12–32) не является функцией ни одного поля
  чека: при одинаковых банке получателя, сумме, получателе, телефоне
  и счёте она полностью разная от операции к операции; линейной
  контрольной суммы по остальным позициям на объединённой выборке
  из 60 ID не нашлось (проверены свёртки по модулям 11–37). Это
  случайный уникальный токен ОПКЦ.
- Следствие для генератора: «придумать» серийную часть нельзя —
  можно только перенести её из настоящего ID (что движок и делает)
  либо принять, что проверяющий, сверяющийся с реальными ID,
  забракует выдуманную комбинацию.

### Номер документа (12 символов)

- Формат: `M` + 11 цифр, первая цифра всегда `7`
  (`M72967127245` … `M73427024333`).
- Монотонно растёт с моментом операции (это сквозной банковский
  счётчик документов, а не функция даты: прирост за 21 секунду внутри
  одной серии — от ~2 тыс. до ~20 тыс.). Точное значение для новой
  операции из полей не выводится.
- Генерация движка: экстраполяция счётчика по моменту операции.
  По корпусу счётчик растёт удивительно ровно: ~18,6 млн в сутки
  (остатки регрессии в пределах ±1,4 млн за 24 дня), поэтому движок
  считает ожидаемое значение из пар (момент операции, номер) всех
  доноров `donors/` и добавляет джиттер внутри наблюдаемых остатков.
  Номер донора + малый сдвиг для новой даты был бы «номером из
  прошлого дня» и как раз попадал под «данные не сходятся».

### Даты и ID внутри PDF

- `/CreationDate` = `/ModDate` = операция + 5 минут (проектная
  конвенция, см. оговорку выше), формат `D:…Z`; файлу на диске
  ставится mtime/atime = CreationDate + 1 c (`rocket_receipt`).
- Trailer `/ID`: новый уникальный, той же длины (128 hex, оба
  значения одинаковы) — `rocket_pdf.reidentify`; донорский оставлять
  нельзя.
- Сумма, телефоны, имена и банк получателя нормализуются движком в
  форматы таблицы полей выше; счёт отправителя без явного параметра
  наследуется от шаблона (все доноры — один отправитель и счёт).

### Глифы и шрифты

- Объединение 20 доноров: `RocketMono-Regular` — 55 символов
  (кириллицы нет `Ъ`, `Ы` в новых донорах нет, но `Ы` есть в старых
  файлах папки; латиница только `ABCGKMN`), `RocketSans-Wide` —
  цифры, пробел и `₽`. CID→символ между донорами не конфликтует.
- Имя/банк с символом вне пула движок честно отвергнет
  (`no donor glyph …`) — нужен настоящий чек Рокета с этой буквой.
- Врезка глифов — вручную в CharStrings INDEX (`rocket_font`):
  все байты CFF до INDEX (Header, Name/String, GlobalSubrs, TopDict,
  FDArray) у всех 500+ сабсетов корпуса внутри семейства идентичны,
  а INDEX — последняя структура файла, поэтому донорская charstring
  копируется в слот-заглушку без пересборки шрифта. Прежняя сборка
  через fontTools выбрасывала GlobalSubrs и ужимала CFF на ~1,2 КБ —
  такой шрифт банк не выпускал.
- Сабсет каждого поля после правки содержит ровно глифы своей строки,
  как у настоящих чеков: неиспользуемые символы вычищаются
  (charstring → заглушка `0e`, CID уходит из `/W` и ToUnicode).

## Ограничения

- Только СБП-чек: в корпусе 18–37 карточных чеков нет, а лежащий в
  папке карточный файл — прежняя генерация (см. «Донор»). Движок
  честно отвергнет не-СБП шаблон.
- Суммы — только целые рубли: копеек в 20 донорах нет, движок
  отвергает некруглую сумму, а не выдумывает формат.
- Глифы — только из настоящих чеков Рокета: в объединённом пуле нет,
  в частности, `Ъ`, `Ю` и большей части латиницы. Имя/банк с такой
  буквой движок отвергнет — нужен настоящий чек с этой буквой в пул.

## Чем сгенерированный файл отличается от настоящего (аудит v7)

Пообъектное сравнение `out/rocket_sample_20261103_0530.pdf` с шаблоном
№ 18 и семейством доноров:

- Размер 88 946 при семействе 88 779–89 421, хвост от `startxref`
  ровно 4 001 байт как у доноров, 181 объект, порядок объектов,
  заголовок, xref и трейлер — как у iText-экспорта.
- Все нешрифтовые объекты, кроме Info (даты) и трейлерного `/ID`,
  байт-идентичны донору; оба изображения (логотип, печать) — донорские.
- Шрифты изменённых строк: префикс CFF до CharStrings байт-идентичен,
  `/Length1` сходится, ширины charstring = `/W`, сабсеты — ровно
  символы своих строк, потоки — zlib level 6 с тождеством
  `compress(decompress(s),6)==s`, как у всех 83 потоков доноров.
- Операторная часть контент-стрима после маскировки hex-строк
  байт-идентична донору (те же `BT/Td/Tf/Tj`, координаты и порядок).

Остававшиеся отличия-«следы» и что с ними сделано:

1. Сабсет-теги шрифтов (`HIHAXQ+…`) раньше оставались донорскими при
   изменённых глифах — теперь при каждой генерации все 26 тегов
   перевыпускаются (`Receipt._rotate_subset_tags`), как у свежего
   экспорта. Это и есть элемент «создания с нуля»: файл больше не
   является клоном конкретного донора по тегам.
2. Полное «создание с нуля» настоящим iText (Java есть, банка —
   iText Core 9.1.0) неосуществимо имеющимися активами: у проекта
   есть только CID-сабсеты банка без Unicode-карты полного шрифта,
   iText из них текст не наберёт. Наш однопроходный refit пишет те же
   объекты в том же порядке и формате, что iText, поэтому он и есть
   практический эквивалент.
3. Хирургический in-place (все офсеты донора) физически невозможен,
   когда строка набирает больше уникальных глифов, чем донорская
   (шрифт номера документа вырос на 300 байт сжатого размера) —
   genuine-экспорт в этом месте тоже меняет размер и офсеты.

### Контролируемые исключения (что точно не причина)

### Полный анализ двух оставшихся пунктов (по трём банкам)

Сверены три независимых источника ID: Рокет (23 уникальных, настоящие),
Яндекс (40, настоящие), МТС (2 свежих от 03.11.2026, файлы владельца).

**Номер операции.** Устройство ID везде одно: заголовок (буква +
UTC дата/время) + серийный токен ОПКЦ. Что различается между банками
и во времени — «эпоха» серийной части (маркер поз. 17–18, сегмент
19–22, хвост 23–32):

| Когда | Банк | Маркер | Сегмент | Хвост |
|---|---|---|---|---|
| сен 2026 | Яндекс | `0B` | 1001–1020 | `0011840301`, `0011850501` |
| 05–12.10 | Рокет | `0G`/`0B` | 1001–1020 | `0011860303` |
| 12.10 вечер | Рокет | `0G` | 1012–1017 | `0011870501` |
| 29.10 | Рокет | `0G` | 1003 | `0011880703` |
| 03.11 | МТС | `0B` | 1004 | `0011881102` |

Выводы: (1) серийный токен не выводится из полей чека и не имеет
публичного алгоритма — придумать его нельзя; (2) эпоха катится во
времени для всей системы (хвосты монотонно растут месяц к месяцу
через разные банки), поэтому октябрьский профиль донора
(`0G/1003/0011880703`) для ноябрьской операции устарел — это и
держало пункт оранжевым даже при «настоящей» серийной части донора;
(3) актуальный профиль на 03.11.2026 по МТС: `0B + 1004 +
0011881102` (сегмент 1004 — заодно модальный и у Рокета). Седьмая
версия движка ставит ноябрьским операциям именно его (до эпохи —
наследует профиль донора); это гипотеза уровня «общая эпоха ОПКЦ»,
проверяется вердиктом.

**Файл изменяли после выгрузки.** Пункт ведёт себя нестабильно
между версиями при неизменной схеме сохранения (у v3/v4 его не было,
у v5/v6 — оранжевый), то есть это не один детерминированный дефект,
а часть суммарной уверенности проверяющего: при подозрительном
номере операции растёт и подозрение на файл. Структурно файл при
этом чист (один проход, без паддинга, шрифты банка). Поэтому
стратегия — сначала закрыть номер операции; если после зелёного
номера файл останется оранжевым, следующим шагом будет хирургический
in-place на исходных офсетах как единственный режим.

### Этап 1 — настоящий карточный чек против СБП и старой генерации

Поля именно карточного чека (по трём донорам, не по аналогии с СБП):

| Поле | В чеке | Правило |
|---|---|---|
| `date` | `03.11.2026 14:54 ПО МСК` | момент операции по МСК, без секунд |
| `amount` | `10 ₽` | как в СБП: целые рубли, пробел — разделитель тысяч |
| `fee` | `БЕЗ КОМИССИИ` | подпись `КОМИССИЯ`, константа |
| `direction` | `ИСХОДЯЩИЙ` | подпись — `ПЕРЕВОД ПО НОМЕРУ КАРТЫ` (не СБП) |
| `card` | `2200 **** **** 9515` | подпись `КАРТА ПОЛУЧАТЕЛЯ`; маска: первые 4 + `**** ****` + последние 4 |
| `bank_to` | `РОСБАНК`, `АЛЬФА-БАНК` или блока нет | подпись `БАНК ПОЛУЧАТЕЛЯ`; короткое имя без юридической формы (в СБП — `ПАО СБЕРБАНК`, `АО "АЛЬФА-БАНК"`); у донора № 45 блока нет целиком — см. ниже |
| `sender` | `АЛЕКСАНДР ЕВГЕНЬЕВИЧ Ж.` | с точкой, как в СБП |
| `account` | `40817 81045 02313 64892` | тот же счёт, что во всём корпусе |
| `bank_from` | `РОКЕТ` | константа |
| `status` | `УСПЕШНО` | константа |
| `doc_number` | `M73559455948` | тот же сквозной счётчик `M7…`, что у СБП |

Чего в карточном чеке **нет** (в отличие от СБП): получателя по имени,
телефона получателя, телефона отправителя и идентификатора операции СБП.
Вместо СБП-ID — карта получателя; связанный номер — только номер документа.

Структура файла (iText® Core 9.1.0, PDF 1.7, 1 `startxref`/`%%EOF`,
`/ID` — пара одинаковых 128-hex, `CreationDate`=`ModDate`):

| Что | СБП (№ 42) | Карта с банком (№ 43/44) | Карта без банка (№ 45) |
|---|---|---|---|
| Размер / объектов / потоков | 88 703 / 181 / 83 | 68 960–68 999 / 142 / 65 | 62 622 / 129 / 59 |
| Шрифтовых сабсетов | 26 | 20 | 18 |
| MediaBox | `420×1116` | `420×918` | `420×852` |

- Каждая пара «подпись+значение» — свой сабсет `RocketMono-Regular` 14 pt,
  сумма — `RocketSans-Wide` 19 pt; сабсет каждого поля содержит ровно символы
  своей строки (проверено по всем полям трёх доноров, включая `*` у карты).
- Контент-стримы № 43 и № 44 после маскировки hex-строк байт-идентичны;
  у № 45 стрим короче и все блоки ниже карты сдвинуты: отсутствие банка —
  это отсутствие целого блока «подпись+значение» и страницы меньшей высоты,
  а не пустое значение. Поэтому чек без банка генерируется из шаблона
  без банка (№ 45), а с банком — из шаблона с банком (№ 44), и наоборот
  движок честно откажет.
- Все потоки доноров — родной zlib level 6 (`78 9c`,
  `compress(decompress(s),6)==s`), как у СБП-корпуса.
- Банк получателя: со слов владельца, карта донора № 45 — ВБ Банк, и блок
  банка в его чеке отсутствует целиком. Напечатанные в донорах формы —
  короткие: `РОСБАНК` (№ 43) и `АЛЬФА-БАНК` (№ 44). ⚠️ Перечень владельца
  «пишутся только ВТБ/Т-Банк/Сбербанк/Альфа» донорами подтверждается не
  полностью: `РОСБАНК` напечатан. Правило движка принято по донорам:
  ВБ Банк → блока банка нет; остальные заданные банки → печатается короткое
  имя без юридической формы (`ПАО`/`АО`/`ООО` и кавычки срезаются,
  `Т-Банк` → `Т-БАНК`, `Сбербанк` → `СБЕРБАНК`, `ВТБ` → `ВТБ`). Формы для
  Сбербанка/ВТБ/Т-Банка в этих трёх донорах не наблюдаются — это гипотеза
  по коротким формам № 43/44, а не измеренный факт.
- Даты и счётчик: `CreationDate` у всех трёх — в ту же минуту, что и
  операция (14:54→11:54:47Z, 14:55→11:55:40Z, 14:57→11:57:43Z), т.е. момент
  выгрузки, а не операция+5 мин — как у свежих СБП-доноров 41/42. Номер
  документа — общий с СБП сквозной счётчик: № 42 СБП 06:42 —
  `M73551331569`, далее карта 14:54 — `M73559455948`, 14:55 — `+15 577`,
  14:57 — ещё `+34 052`; локальная скорость ≈16–17 тыс./мин. Якорь для
  карточного генератора — свежайшая точка корпуса (№ 45, 14:57).
- Глифы: карточный пул даёт `RocketMono-Regular` 45 символов (в т.ч. `*`,
  которого в СБП-полях нет). Для 42 общих CID карточного и СБП-пулов
  charstring'и байт-идентичны, конфликтов CID→символ нет — пул карточного
  движка собирается из всех настоящих чеков Рокета (`donors_card/` +
  `donors/`), старые сгенерированные файлы в пул не входят.

Старая генерация `rocket_card_check.pdf` против настоящих № 43/44: раскладка,
позиции, 142 объекта, MediaBox `420×918` и операторная часть контент-стрима
(после маскировки hex) совпадают — она патчилась из настоящего карточного
донора с банком. Отличия — в связанных данных, поэтому эталоном полей быть
не может: `CreationDate` (05.10 00:17Z) раньше самой операции
(06.10 21:05 МСК), номер документа — круглая заглушка `M70123456789`
(эпоха октября — `M72…`/`M73…`), банк — юридическая форма `ПАО СБЕРБАНК`
вместо короткой, карта и хвост счёта — `…1111`.

- Поля (шапка, все страницы повторяют только верх/низ): `ВЫПИСКА ПО

### Поля и связность (измерено, не из чеков)

- Тождество шапки во всех 8: `исходящий = входящий + поступления −
  расходы`. `ДАТА ПОСЛЕДНЕГО ДВИЖЕНИЯ` — дата последней операции
  периода; у пустых выписок (11, 18) значения нет (подпись есть).
- `БАЛАНС НА НАЧАЛО ДНЯ` единственной напечатанной дневной группы
  во всех донорах с операциями равен входящему остатку шапки.
- Строка операции: `ВРЕМЯ` = `ЧЧ:ММ`, `КОД ОПЕРАЦИИ` = 11 цифр,
  `ОПИСАНИЕ` (шаблоны ниже), `СУММА` = `+X,XX RUR` (поступление)
  или `-X,XX RUR` (расход). Итоги `ВСЕГО …` и обороты шапки в
  согласованных донорах (11, 12, 15–18) равны суммам напечатанных
  операций по знаку.
- **Аномалия настоящих № 13/14 (фиксируем, не копируем):** напечатана
  только первая дневная группа периода (05.10 / 12.10), обороты и
  дата последнего движения в шапке при этом — за весь период
  (№ 14: напечатано +126/−120 и `ВСЕГО` под группой — те же 126/120,
  а шапка +1 284/−1 271 и последнее движение 15.10). Т.е. банковский
  генератор сам печатает не все дни, а итоги шапки считает по всем.
  Наша генерация так не делает: у нас напечатанные операции, итоги,
  обороты и остатки сходятся между собой (как в № 12/15).
- Связь с чеками — доказана на № 12 (операции 03.11.2026 дословно
  равны чекам 41–45): `КОД ОПЕРАЦИИ` выписки = номер документа чека
  без `M` (`M73551326616` → `73551326616`), сумма — со знаком минус
  для исходящих, SBP-ID в описании — байт-в-байт ID чека, время и
  телефон — из чека. Исходящий СБП:
  `ПЕРЕВОД СОГЛАСНО РАСПОРЯЖЕНИЮ / СБП / {ДД.ММ.ГГГГ ЧЧ:ММ} / СЧЕТ
  ПЛАТЕЛЬЩИКА {счёт} ТЕЛ. {10 цифр без +7}. БЕЗ НДС / {SBP-ID} СЧЕТ
  КОРРЕСПОНДЕНТА 30232 810 4 5014 0000088 (ФИЛИАЛ "КОРПОРАТИВНЫЙ"
  ПАО "СОВКОМБАНК").` Входящий СБП (чеков на него нет):
  `ЗАЧИСЛЕНИЕ ПЕРЕВОДА ДЕНЕЖНЫХ СРЕДСТВ/СБП/{ГГГГ-ММ-ДД
  ЧЧ:ММ:СС}/007{10 цифр}/{SBP-ID} СЧЕТ КОРРЕСПОНДЕНТА
  30233 810 3 5014 0133326 (ФИЛИАЛ …).` Перевод по карте:
  `ВНЕШНИЙ ПЕРЕВОД СО СЧЕТА {счёт} {ИМЯ ОТЧЕСТВО Ф.} НА КАРТУ
  {первые 6 цифр}*{последние 4} {ГГГГ.ММ.ДД ЧЧ:ММ} УСТРОЙСТВО
  0017I001739` — ⚠️ в чеке по карте видны только первые 4 и
  последние 4 цифры, цифры 5–6 для выписки из чека не восстанавливаются
  (у № 43: чек `2200 **** **** 9515` → выписка `220039*9515`).
  Пополнение (№ 14/16, чека нет): `ПОПОЛНЕНИЕ ДЕНЕЖНЫХ СРЕДСТВ
  АВТОРИЗАЦИЯ №{11 цифр},{дата} {время},2200********{4 цифры},
  {сумма без копеек}RUR,SAINTPETERSBU,MCC 6536,28294804\RU\
  SAINTPETERSBU\VTB\ 28294804\`, сумма со знаком `+`.
  В № 13 время в колонке может отличаться от времени в описании
  на минуту (03:06 против 03:05 в описании и в SBP-ID) — у нас
  колонка, описание и ID всегда про один момент.
- Счёт `40817810450231364892`: `40817` (физлицо) + `810` (RUR) +
  ключ (9-й разряд) + `5023` (подразделение) + 7 цифр лицевого;
  последние 5 цифр — хвост лицевой части (`…13|64892`). Ключ
  пересчитывается по письму ЦБ № 515 (префикс — последние 3 цифры
  БИК, веса `7,1,3` по кругу, ключ = младший разряд от
  `(сумма с нулём вместо ключа mod 10) × 3`). Из трёх БИК
  Совкомбанка (головной `044525987`, «Корпоративный» `044525360`,
  «Центральный» `045004763`) ключ донора `4` воспроизводит только
  префикс `763` — на нём движок и считает ключ при смене хвоста
  (корреспондентские счета 30232/30233 из описаний тем же алгоритмом
  сходятся с префиксом «Корпоративного» `360` — алгоритм не выдуман).
  Случайная смена последних 5 цифр меняет ключ и все вхождения счёта
  (шапка + каждое описание), а не только хвост.

### Этапы 2–5 — что сделано (03.11.2026)

- Этап 2, байт-в-байт: все 8 доноров открываются и сохраняются без
  изменений побайтово — и на уровне `rocket_statement.StatementPdf`,
  и через модель `Statement` (`test_statement.py`, Stage 2 — PASS).
  Пересборка повторяет продюсерский порядок: физические стрим-объекты
  по возрастанию номеров, затем ObjStm, затем xref-stream
  (`W [1 2 2]`), неизменённые стримы копируются как есть, изменённые
  пересжимаются на уровне 9.
- Этап 3, одно поле родным шрифтом: смена только суммы операции
  (`+100,00` → `+250,00 RUR`, шрифт поля — IBM) перечитывается
  обратно, остальные строки не меняются, `qpdf --check` чистый, все
  Flate-стримы — `78 da`. Отдельно доказано (Stage 3b/3c): шрифт,
  собранный нашим патчером под текст донора, байт-идентичен
  собственному шрифту донора под тот же текст и тот же
  `head.modified`, включая **врезку недостающих глифов** в донор № 18
  до набора донора № 15 (обе гарнитуры). Врезка копирует глиф,
  компоненты составных глифов, `hmtx`, cmap и класс GDEF из
  настоящих выписок; неиспользуемые глифы глушатся, как у продюсера.
  Сабсет-теги не меняются: у всех доноров они одинаковые
  (`SBKLGE`/`DUFPOI`). TJ-корректировки после глифов берутся из
  статистики по донорам выписки (пара символов → число), для
  строк той же длины сохраняются позиционно исходные.
- Этап 4, все поля и связанное: период и дата выдачи на каждой
  странице, ФИО (+ то же ФИО в outline-заголовке), счёт с
  пересчитанным ключом во всех вхождениях, входящий/исходящий
  остатки, обороты, дата последнего движения, дневная группа
  (`{дата}` + баланс на начало дня = входящий остаток), строки
  операций (время, код, описание по шаблону вида операции с
  переносом по измеренной ширине колонки, сумма со знаком) и итоги
  `ВСЕГО …`. Подписи итогов и баланса дня сдвигаются вместе со
  значениями, как у доноров (пара «подпись+значение» выровнена
  вправо). Связи: исходящий = входящий + поступления − расходы;
  итоги = суммы напечатанных операций; коды операций строго растут
  со временем (в т.ч. между кодами настоящих чеков-якорей); SBP-ID
  заполняющих операций строятся движком чеков от ближайшего по
  времени настоящего ID выписки; коды — той же моделью счётчика
  `M7…` чеков (без `M`). `head.modified` обоих шрифтов = момент
  генерации, mtime файла = тот же момент +5 с (у доноров +4…+10 с).
  Количество операций — 0…10; доноры-шаблоны по количеству:
  0 — № 18, 1–4 — № 15, 5–6 — № 12, 7–9 — № 14, 10 — № 13
  (у № 13 продюсер итоги под группой не печатает — так и у нас при
  10). При несовпадении числа строк описаний с шаблоном делается
  релайаут одной дневной группы: плашки строк трансформируются,
  BT-блок операций перестраивается из собственных прогонов шаблона,
  итоги/подвал и печать сдвигаются на ту же дельту. Операции —
  одного календарного дня внутри периода (дневная группа доноров).
- Этап 5, функция в отдельном модуле `rocket_statement.py`
  (готовые движки чеков не тронуты):

  ```python
  from rocket_statement import generate_rocket_statement
  generate_rocket_statement(
      period_start="16.10.2026", period_end="23.10.2026",
      issue_date="03.11.2026",
      holder_name="Жеребятьев Александр Евгеньевич",
      account="40817810450231364892",   # или account_tail="12345"
      opening_balance="16,00",
      operation_count=6,                # сколько платежей выбрать
      operation_date="20.10.2026",      # день заполняющих операций
      receipt_paths=["receipt_rocket_42.pdf"],  # чек -> операция
      output_path="out/rocket_statement_….pdf",
  )  # -> pathlib.Path
  ```

  Удобство: даты принимаются строками/датами, сумма остатка —
  строкой; `account_tail`/`random_account_tail=True` меняют
  последние 5 цифр с пересчётом ключа; `operations=[…]` — явные
  операции словарями (`kind` `sbp_out`/`sbp_in`/`card`/`topup`,
  `datetime`, `amount`, готовые `code`/`sbp_id`/`card` …).
  Если задан один чек (`receipt_paths`), а `operation_count`
  больше, остальные операции при `fill_random=True` (по умолчанию)
  генерируются из настоящих операций доноров: виды, суммы, маски
  карт и эры SBP берутся из пулов выписок, коды и SBP-ID — из
  корпусов чеков; баланс при этом не уходит в минус (первая
  заполняющая операция при необходимости делается входящей).
  Честные отказы: операция вне периода, операции на несколько
  дней, больше 10 операций, перерасход остатка без заполняющих,
  буква вне пула глифов выписок.

## Гипотезы

- Если третью версию снова забракуют, первые подозреваемые:
  1. «Номер операции»: в СБП-ID может быть контрольный механизм на
     непрозрачных сегментах (поз. 12–22), не видимый на корпусе из 37;
     либо допуск проверяющего на счётчик номера документа уже, чем
     остатки нашей регрессии (±1,4 млн ≈ ±2 часа счётчика);
  2. CreationDate: у свежескачанных доноров это момент выгрузки, а не
     операция+5 мин; если проверяющий сверяет CreationDate с «сейчас»
     загрузки, конвенцию придётся менять на момент генерации;
  3. хвост СБП-ID (поз. 23–32): у будущих операций может появиться
     следующее «поколение» после `0011880703`.
